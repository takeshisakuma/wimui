# Tokenization Exceptions (トークン化除外ルール)

WIM UI では、保守性と一貫性を高めるためにデザイントークンへの移行を推進していますが、以下のケースについては、**「意図的なハードコード」**としてデザイントークンの適用を免除しています。

これらを無理にトークン化（抽象化）すると、コンポーネントの視覚的整合性が失われたり、メンテナンス性が低下したりする恐れがあるためです。

---

## 1. 幾何学的整合性 (Geometric Harmony)
コンポーネント内部のパーツ同士が数学的な比率や黄金比、特定の形状（正方形、アイコンのグリッド等）を維持するために必要な値。

- **理由**: トークンスケール（例: 4px刻み）に無理に当てはめると、パーツ同士が重なったり、意図したアスペクト比が崩れたりするため。
- **具体例**: 
  - `HamburgerMenu`: 線の厚み（2px）、間隔（6px）、全体の高さ。
  - `LoadingSpinner`: 円の円周計算に基づくストローク値。

## 2. 描画補正 (Browser Rendering Fixes)
ブラウザのレンダリング（アンチエイリアシング、サブピクセルレンダリング）による微妙なボケやズレを解消するための微細な値。

- **理由**: これらは「デザイン上の意味」ではなく「実装上の技術的補正」であるため。
- **具体例**:
  - `margin-top: -1.5px;` (垂直方向の中央揃えの微調整)
  - `box-shadow: 0 0 1px ...` (ボーダーのジャギー防止)

## 3. 構造上の固定寸法 (Structural Logic)
特定のレイアウトにおいて、コンテンツの最小限の視認性や操作性を担保するために、他との兼ね合いを無視してでも死守すべき寸法。

- **理由**: グローバルな間隔設定（Spacing）に依存させると、将来的にグローバルの余白を変更した際に、特定の複雑なレイアウトが壊れる（オーバーフローする等）のを防ぐため。
- **具体例**:
  - `Kanban`: 列の固定幅（280px）。
  - `Splitter`: ハンドルの当たり判定幅（8px）。

## 4. インタラクションの物理挙動 (Interaction Physics)
ホバー時やアクティブ時の「感覚的なフィードバック」に使用される数値。

- **理由**: セマンティック（意味論的）な値ではなく、アニメーションの「味付け」に近い性質を持つため。
- **具体例**:
  - `transform: scale(0.98);` (クリック時の沈み込み)
  - `filter: brightness(1.1);` (ホバー時の発光)

---

## 運用ルール
今後、コンポーネントにハードコード値を導入する場合は、上記のいずれかのカテゴリに該当するかを確認してください。該当しない「px」や「カラーコード」は、原則として `src/tokens/` 下のデザイントークンに移行する必要があります。
